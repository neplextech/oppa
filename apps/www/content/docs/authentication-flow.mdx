---
title: Authentication Flow
description:
  Provider-neutral PKCE pairing, token exchange, refresh, and
  credential storage.
---

OPPA uses an authorization-code flow with PKCE. The integrating
platform owns login, account selection, approval, code issuance, token
issuance, permissions, and revocation.

## Pairing sequence

1. OPPA generates a cryptographically random state and PKCE verifier.
2. It binds an ephemeral callback listener to `127.0.0.1`.
3. It opens the selected service's validated authorization URL in the
   system browser.
4. The platform authenticates the user and redirects a short-lived
   code to the loopback callback.
5. OPPA compares state in constant time, accepts the code once, and
   closes the listener.
6. OPPA exchanges the code and verifier at the configured token
   endpoint.
7. Tokens, including a refresh credential when the provider issues
   one, are written through `oppa-platform` secure credential storage.

The callback never binds to `0.0.0.0`, a LAN address, or a fixed
public port. It expires quickly and stops after success, timeout, or
cancellation.

## Token format

OpenPrinter does not prescribe JWTs. The server authentication
callback receives the Bearer token and may validate an opaque
credential, signed device token, database-backed session, or JWT.

## Storage

Access and refresh credentials must not be stored in SQLite, product
configuration, diagnostic bundles, or logs. `oppa-platform` provides a
secure credential interface backed by the operating system credential
service. An in-memory implementation exists only for tests.

## Revocation and refresh

An invalid refresh response moves the agent to an
authentication-required state and removes unusable credentials.
Network failures do not erase a still-valid credential. Refresh work
is bounded and never logs the token body.

Changing the authorization, token, or gateway URL is a provider
boundary change. OPPA clears the previous credentials before saving
the new endpoints and requires a new pairing flow.
